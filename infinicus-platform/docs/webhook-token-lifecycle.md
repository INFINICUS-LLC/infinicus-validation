# Webhook token lifecycle — Data Acquisition webhook intake

Scope: the bearer token that authenticates `POST /v1/webhooks/data-acquisition/:token`.
Everything here is verified against the code on this branch unless marked **not verified**.

## Architecture boundary

The webhook is an **inbound Data Acquisition (DAL) capability only**:

```
external sender
  → authenticated webhook credential (this token)
  → DAL intake (validation, quality scoring, provenance, idempotency)
  → governed DAL → BO publication contract
  → downstream lifecycle
```

It does **not** write to Business Operations, Business Intelligence, the Digital Twin, Simulation,
AI Decision Intelligence, Approved Business Action, Outcome Monitoring or Continuous Learning. A
delivery creates a DAL collection run; anything downstream happens only through the existing,
governed DAL publication path. Any change that gives the webhook a direct write path to another
layer is an architecture conflict and must be escalated, not implemented.

## Token format and storage

| Item | Value |
|---|---|
| Format | `<prefix>.<secret>` — prefix = 6 random bytes (12 hex chars), secret = 32 random bytes (64 hex chars) |
| Generated by | `ConnectorRepository.generateWebhookToken` (Node `crypto.randomBytes`) |
| Stored | `data_acquisition.connectors.webhook_token_prefix` (unique, partial index) and `webhook_token_hash` = SHA-256 of the full raw token |
| Never stored | the raw token and the secret half. A database or backup read yields no usable token |
| Verification | prefix lookup via `find_connector_for_webhook()`, then constant-time comparison of SHA-256 hashes (`webhookTokenHashesMatch`) |
| Failure mode | unknown prefix and wrong secret both raise the same `WebhookAuthenticationError` (401); the caller cannot tell which |

`find_connector_for_webhook()` is the single cross-tenant read in the DAL (an inbound webhook has no
tenant context). It is `SECURITY DEFINER` with a **pinned `search_path = pg_catalog, pg_temp`**, and
`EXECUTE` is **revoked from PUBLIC** (migration `0171_create_da_webhook_token_lookup.sql`). The
application role receives `EXECUTE` through `infrastructure/database/scripts/grant-app-role.sh`
(migrations in this repository contain no role-specific `GRANT`s). Both properties are asserted by
integration tests in `packages/database/tests/da-repositories.integration.test.ts`.

## Generation and one-time display

`POST /v1/businesses/:businessId/data-sources/:sourceId/connectors/:connectorId/webhook-token`

- Requires `da:admin` and an active subscription; the connector must be of type `webhook`.
- Returns `201 { token, webhookUrl }` **once**. There is no endpoint that can read the token again.
- This route deliberately does **not** use `requireIdempotencyKey`. The idempotency layer stores every
  completed response body in `api.idempotency_keys` and replays it on retry; for this route that would
  persist the raw token in plaintext. An integration test asserts that neither the first nor a
  regenerated token's secret ever appears in `api.idempotency_keys`.
- Treat the response as a secret: the caller must hand it to the sender over a secure channel and must
  not log it. The URL contains the token.

## Rotation

Calling the generate endpoint again **is** rotation.

- The prefix and hash are overwritten in one `UPDATE`; the previous token stops working **immediately**.
  There is **no overlap window**: the sender must be updated at once or deliveries return 401 until it is.
- Each rotation increments the connector `version`. **Not verified:** whether a dedicated audit/outbox
  event is emitted for rotation; none was found in this review.
- Recommended practice: rotate on a schedule agreed with the data-source owner, after any staff change
  affecting the sender, and always after a suspected exposure (below).

## Invalidation (without issuing a new token)

Deliveries are accepted only while **all** of these hold, otherwise the request is rejected after the
token check:

1. the connector status is `active`;
2. the data source status is `active`;
3. the data source has an associated business;
4. neither the connector nor the data source is soft-deleted (the lookup function excludes deleted rows).

To invalidate a token without rotating, set the connector status to a non-`active` value
(`PATCH .../connectors/:connectorId/status`) or set/delete the parent data source
(`PATCH .../data-sources/:sourceId/status`, `DELETE .../data-sources/:sourceId`); all require `da:admin`.
There is no connector-delete endpoint and no dedicated "revoke token and keep connector active" endpoint;
rotating and discarding the new token is the equivalent.

## Compromise handling (runbook)

If a webhook URL or token may have been exposed (pasted in a ticket or chat, a sender-side log, a proxy
log from before redaction was in place, a lost device):

1. **Contain** — rotate the token now (generate endpoint). If the sender cannot be updated quickly, first
   set the connector to non-`active` to stop intake, then rotate and re-activate.
2. **Scope the window** — query `data_acquisition.webhook_receipts` and `collection_runs` for that
   connector between the suspected exposure time and the rotation (`received_at`). Compare
   `external_event_id`, `request_id`, `payload_hash` and the stored `headers` against what the sender
   actually produced. Receipts do not record a source IP column; any client-IP header added by the proxy
   appears only inside `headers`, and Caddy's access log (remote IP, URI redacted) is the better source.
3. **Quarantine data** — any collection run created in the window that the sender did not produce should
   be treated as untrusted. Do not publish its publication package to Business Operations; if already
   published, raise it through the data-quality process rather than editing history (provenance and
   lineage must stay intact).
4. **Clean up logs** — logs written *before* redaction was deployed may contain tokens in the URL. Rotate
   any token that could appear there and restrict or expire those logs per your retention policy.
5. **Record** — note the incident, the rotation time and the affected connector in the incident process
   (`/v1/incidents` for platform incidents).

## Log redaction

The token travels in the URL path, so every place that records a URL must not record it.

| Layer | Behaviour | Verified |
|---|---|---|
| Fastify request/response logs | `disableRequestLogging: true`; no default access line is written | by code (`apps/api/src/app.ts`) |
| API audit log and error events | the route **template** (`/v1/webhooks/data-acquisition/:token`) is used when a route matches; for unmatched requests the raw URL fallback now goes through `redactUrl()` (`apps/api/src/redactUrl.ts`) | unit test `tests/redactUrl.test.ts` |
| `404 route_not_found` response body | echoes the method and a **redacted** URL | by code |
| Caddy access log (Hetzner and OCI Caddyfiles) | `format filter` rewrites `/v1/webhooks/data-acquisition/<token>` to `/v1/webhooks/data-acquisition/REDACTED` before the entry is written | live test with Caddy 2.8.4: a request carrying a fake token produced `.../REDACTED` and zero token characters in the log file; `caddy adapt` passes for both Caddyfiles |

Residual risks (not covered by this change):

- Caddy's **error** logger (for example upstream connection failures) is separate from the access log and
  may include the request URI. Add a global `log` filter in Caddy's global options if error logs are
  retained or shipped.
- Any log written by systems outside this repository: sender-side logs, CDN/WAF/load balancer logs, and
  anything that stores full URLs. Treat the URL as a secret when integrating.
- Logs written before this change contain tokens. See compromise handling, step 4.

## Rate limiting

The API registers one global `@fastify/rate-limit` limiter (`RATE_LIMIT_MAX` per `RATE_LIMIT_WINDOW_MS`,
default **100 requests per 60 s**), keyed by `request.ip`. See the pull request for the findings about
how that interacts with Caddy and with webhook delivery/retries; it was **not** changed by this
documentation.

## Known limitations

- Rotation has no overlap window (above).
- Request headers sent by the webhook sender are persisted verbatim in `webhook_receipts.headers`; no
  header is currently excluded (for example `Authorization` or `Cookie` if a sender includes them).
