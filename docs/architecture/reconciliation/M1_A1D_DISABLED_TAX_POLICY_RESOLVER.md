# M1-A1D — disabled tax-policy authority resolver

Base: `main` at `b0d4abe`. Status: **synthetic-fixture preparation only**. The accepted M1-A1C platform governance invariants are represented; no jurisdiction policy, tax rate, exemption, rounding stage, permission or POS amendment is ratified or activated.

`resolveDisabledTaxPolicy` is a pure BO-runtime function with no database client, writer or POS call site. It chooses exactly one active policy and one matching sellable classification at a supplied trusted BO UTC instant using half-open `[effectiveFrom, effectiveUntil)` intervals. It requires exact tenant/workspace/business, policy and classification ID/version, currency/exponent from the platform's supported currency table, matching classification-to-policy references, explicit class and price treatment, and syntactically valid provenance digests. Missing, overlapping, expired, revoked, duplicate-version, foreign-scope, stale, unknown or malformed fixtures fail closed. Fixture `active` and `authorityReference` are *claims in test data*, not verified human approval.

Every result has `authoritative: false` and `activationAllowed: false`; even a candidate contains `AUTHORIZATION_DISABLED`. The returned candidate records policy/classification IDs and versions, jurisdiction, currency/exponent, explicit `TAXABLE`/`ZERO_RATED`/`EXEMPT`, `INCLUSIVE`/`EXCLUSIVE`, source digests, supplied authority reference and scope. It contains no tax amount or calculated payable. `TAX_POLICY_ACTIVATION_ENABLED` is a constant `false`.

The module imports only the existing pure `minorUnitsOf` lookup from the database package. `OrderRepository.complete`, `OfflineSaleRepository`, and their API routes do not call the resolver; their current behavior, including `accepted_with_difference`, is unchanged. BO remains financial-calculation owner; this module cannot grant a canonical permission or claim legal classification authority.

Focused tests cover effective boundaries, missing/overlapping/revoked/expired and duplicate policy/classification versions, stale bindings, foreign scope, unknown class/treatment, inclusive/exclusive and exempt/zero-rated distinctions, currency precision, invalid provenance, repeated deterministic calls and absence of a production POS call site. Fixture mutations from active to revoked and from valid to stale/foreign/unknown states always leave activation closed. No PostgreSQL integration test is appropriate because this block has no persistence or database read.

Existing sales, OM VERIFIED/FAILED and CL learning remain unchanged.
