| `apps/api/src/schemas/` (35 Zod-importing API source files; 21 one-argument `z.record` uses across schema files) | **High**: Zod 4 requires explicit record key and value schemas; JSON payloads and dynamic maps must retain the intended key/value acceptance rules. | Replace each one-argument record with an explicit, equivalent key schema and test accepted/rejected values; do not choose a generic permissive substitute without contract evidence. | `schemas/products.ts`, `schemas/orders.ts`, `schemas/common.ts`, `schemas/financialIntelligence.ts`, plus other default/coercion schemas | **Medium to high**: defaults and optional parsing, `z.coerce.boolean()`, number/date coercion, and Zod 4 default short-circuiting can alter inferred types or outputs. | Compare omitted, null, empty, string, numeric, and repeated query values. | All route `response` schemas, notably auth tokens, offline sales, orders, billing, BI/OM results | **High**: provider 7 uses `safeEncode` for responses rather than provider 4's `safeParse` path. Preserve 204 and nullable response contracts. |
| `apps/api/src/app.ts` Swagger registration and `/documentation/json` | **High**: Zod 4's JSON Schema output may alter required/optional fields, strictness, nullability, formats, defaults, unions, security metadata and component references. | Generate old/new OpenAPI documents, diff after removing only noncontract ordering, run an OpenAPI parser, and review every semantic difference before approval. |
| `apps/web` Zod client parsers (18 importing files) | **Medium**: client rejection/normalization could differ from API behavior. | Match API response fixtures to web parsers; cover auth session, scoped resources, sales/reporting and error payloads. |

Zod 4 commonly changes error issue formatting and `ZodError` APIs. The API's error handler currently returns `error.message` for validation failures inside `{ error: { code: 'validation_error', message, correlationId } }`; compare exact envelope and sensitive-field redaction rather than assuming message text is stable. Plain `z.object()` strips unknown keys while `.strict()` rejects them in current Zod 3 tests; verify both behaviors under the candidate. Zod 4's default handling differs where a default bypasses transformations; compare every production default instead of imposing a global rewrite. Deprecation or changed TypeScript signatures (for example string-format helpers) should be fixed only where tests establish equivalent behavior.

## Ordered implementation proposal — requires separate authorization

1. Freeze baseline fixtures from the current Zod 3 app: validation accept/reject cases, normalized request values, 400 envelopes, response JSON and OpenAPI document. Include authenticated and unauthenticated paths, cross-tenant refusal, POS/offline checkout and financial cases.
2. In an isolated development branch, test provider 6.1.0 and 7.0.0 against Zod `>=4.6.6` with strict peer resolution. Select the smallest supported version whose compiler and serialization behavior can preserve the fixtures. Confirm `openapi-types` peer and a single runtime Zod instance.
3. Adapt API and web Zod schemas and types where necessary, starting with explicit `z.record(key, value)` calls. Keep strictness, unknown-field handling, coercion, defaults and security error envelopes unchanged. Reconcile declared but unused Zod dependencies separately.
4. Apply only same-major `fast-uri` fixes (3.1.9 and 4.2.3), reconcile both override locations, regenerate the lockfile with pinned pnpm, and verify that both branches resolve to patched versions.
5. Run lint, all package typechecks/builds, API and web unit/integration suites, disposable PostgreSQL regressions, architecture guards, OpenAPI semantic diff, serialization fixtures, authentication/tenant isolation, POS/offline/idempotency, and the dependency scan. Treat a changed public contract or a remaining high advisory as a blocker. Obtain owner review before merge or deployment.

No Zod 4 trial, API behavior change, or patched-lockfile CI result is claimed in CI-SEC-2A. Existing advisory exposure remains until an authorized implementation passes these gates.
