## 2. Block 2 — canonical risk governance (implemented)
- One authoritative definition: `CANONICAL_BASE_RISK_CLASS` in `handoff-contracts/src/authorized-action-package/canonical-actions.ts`, next to the other per-type governance sets (`SIMULATION_NOT_APPLICABLE_ALLOWED`, `STRUCTURED_ADI_PROPOSAL_REQUIRED`): `inventory_reorder_policy_update@1` → `medium`. Per `code@schemaVersion`, never global. It is deliberately **not** a field of `ActionTypeContract`: that interface is compared with workspace-stored definitions and the existing governance sets already live beside it, so a second registry is not created and the stored-definition comparison is untouched.
- ADI does not classify: `deriveRiskClass` (P0-3) gains one input, `canonicalBaseRisk`, a deterministic floor (MAX with persisted severities, generator level, human raise — contextual evidence can only raise it). The producer passes `canonicalBaseRiskClass(...)`; it contains no risk literal (guard test).
- ABA consumes it: `packageIssuancePolicy` refuses (`RISK_POLICY`) a package whose persisted recommendation risk is *below* the action type's canonical base. Unclassified keeps its P0-2 meaning (treated as high, never below a base). The package still records the persisted class; no `aap/1` change.
- Effect on the approval tier: producer-made proposals are now `medium` (required approver tier 2) instead of unclassified/high (tier 3). Test fixtures that used `low` for this action type were updated to `medium` (shared `issuanceFixture`, API `APPROVABLE_FACTS`).

## 3. STOP-AND-REPORT — why Blocks 3–10 were not started
The block text says to stop if the source data cannot be ingested through an existing authoritative DAL path without inventing a new source of truth, and the principal proof forbids direct BO seeding. Four inputs cannot be obtained that way, and two of the four are *deliberate* prior owner rulings:
1. **Item and warehouse identity** have no writer at all. Adding `inventory_item` / `warehouse` mappers plus BO commands extends the existing mapper path (BO stays the truth) but creates a new canonical-entity creation path — a design decision, not a test fixture.
2. **Baseline reorder policy.** A balance created by DAL movements is 0/0/UNSET, and the producer correctly returns no recommendation for an unset baseline (`FIRST_CONFIGURATION_OPTION = NO`). The block asks for "existing reorder policy state" through DAL, but Block E (owner-ruled) forbids the intake path from configuring it. These two cannot both hold.
3. **Declared currency** is a business-admin act by Block C, not a DAL fact.
4. **SIM→ADI.** The locked package chain is BO→BI→DT→SIM→ADI; ADI's package intake takes a Simulation publication package. Under C-1 no simulation exists for this action, so a *package-intake* ADI entry cannot be satisfied without fabricating one. AC-1's producer writes ADI records directly; Block 7 must say whether the BI/BDT boundary is a producer precondition (my proposal) or whether ADI intake is to be amended.

## 5. Block 3 — DAL ingestion of the first-action source facts (owner rulings D1–D4 applied)
What changed (Business Operations intake mapper registry and command executor; no migration, no DAL change, no contract change):
- **`inventory_item` v1 and `warehouse` v1 record types (D1)** -> BO commands `create_inventory_item` / `create_warehouse` in `OperationalCommandExecutor`. Identity is a natural key (SKU / warehouse code, strict pattern, bounded names); BO generates the id; scope always from the authenticated context; `source_system = INFINICUS_DA`, `source_record_id = submission#index` (traceable to the DAL provenance record). A replay with identical attributes is a no-op; the same key with different attributes is refused (master data is not changed by intake).
- **`inventory_movement` v3**: the item and warehouse may be addressed by natural key (`sku`, `warehouseCode`) because a source cannot know BO identifiers (exactly one of id/key each), and the record may state its business instant `occurredAt` (demand history; never in the future on the database clock). It maps to `record_keyed_inventory_movement`, which resolves the keys inside the business scope (fail closed) and calls the SAME single movement writer. A v2-shaped record maps exactly as before.
- **Not through DAL, by ruling**: the baseline reorder policy (D2: a later BO-owned route; Block E intact) and the declared currency (D3). The test asserts the balance stays `UNSET` 0/0 and no currency is declared after ingestion.
- Proof: `apps/api/tests/ac2-dal-first-action-ingestion.integration.test.ts` (6 tests, real PostgreSQL, production `buildApp`, production DAL service and BO intake route): DAL accepts 15 records with 15 provenance records and writes no operational row; BO intake canonicalizes warehouse, item, receipt (1000 units, cost 10 USD, business instant 5 days ago), 12 issues on 12 distinct days and the balance (100); replay is idempotent; unknown SKU / future instant / cost without currency each refuse the whole package with nothing persisted; a conflicting master record is refused; scope in the record is ignored and another tenant cannot consume the package.
- Honest limit: the mapper-to-command-to-row path is proven; the BO item/warehouse creation still has no HTTP route of its own (it is intake-only by design).

## 6. Block 4 — Business Operations canonical truth (D2, D3 applied)
- **BO reads what DAL delivered, and only BO**: `InventoryPolicyFactsRepository` (BO's own facts reader) sees the ingested item, the single balance, the latest receipt (cost 10, USD) and the dated demand history (12 issues, 900 units). No BO reader consults a Data Acquisition table; Data Acquisition runtime references no BO or canonical inventory table (architecture guard).
- **Baseline policy (D2)**: new BO-owned route `PUT /v1/businesses/:businessId/inventory-items/:itemId/warehouses/:warehouseId/initial-reorder-policy` (`bo:admin`, Idempotency-Key, audited `bo.reorder_policy.initial_configured`, atomic with the change). It performs the **first** configuration only: the executor refuses (`ReorderPolicyAlreadyConfiguredError`, HTTP 409) a balance that is already `CONFIGURED`, checked under the row lock (`requireState: 'UNSET'`), so changing an existing policy stays an authorized action. Values must be positive, at most four decimals, never rounded. It reuses the single writer (`configureInventoryReorderPolicy` -> `apply_inventory_reorder_policy`, migration 0196); no new SQL, no migration. The DAL intake mappers still cannot produce the command (guard).
- **Currency (D3)**: the explicit business-admin declaration is used as the currency source in the proof; DAL never declares it.
- **Proof** (`ac2-bo-canonical-truth.integration.test.ts`, 7 tests; `ac2-bo-canonical-writer.architecture.test.ts`, 7 guards): with the baseline unset and no currency BO derives nothing (`EVIDENCE_UNAVAILABLE`, `BASELINE_UNSET_OR_ZERO`); the first-policy route configures UNSET -> CONFIGURED once with its audit row; a second call is 409 and changes nothing; unauthenticated / viewer (no `bo:admin`) / other tenant / non-positive, unknown or over-precise values / missing Idempotency-Key are refused; the application role cannot write the reorder columns directly; with baseline and declared currency the BO derivation yields the compliant single step 175/190 from DAL-ingested truth and writes nothing.
- Guards extended additively (no guard weakened): the Block E, B2b, B2c, B2d and Block C architecture guards now list the one new carrier of the command literal (the BO first-policy service) and the one new consumer (the route).
- Honest limit: item and warehouse creation still has no HTTP route of its own (intake only, by design); BI/BDT and the ADI boundary are Blocks 5–7.
