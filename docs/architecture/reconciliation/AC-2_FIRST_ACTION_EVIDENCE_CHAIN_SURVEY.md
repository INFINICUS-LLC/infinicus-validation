## 2. Block 2 — canonical risk governance (implemented)
- One authoritative definition: `CANONICAL_BASE_RISK_CLASS` in `handoff-contracts/src/authorized-action-package/canonical-actions.ts`, next to the other per-type governance sets (`SIMULATION_NOT_APPLICABLE_ALLOWED`, `STRUCTURED_ADI_PROPOSAL_REQUIRED`): `inventory_reorder_policy_update@1` → `medium`. Per `code@schemaVersion`, never global. It is deliberately **not** a field of `ActionTypeContract`: that interface is compared with workspace-stored definitions and the existing governance sets already live beside it, so a second registry is not created and the stored-definition comparison is untouched.
- ADI does not classify: `deriveRiskClass` (P0-3) gains one input, `canonicalBaseRisk`, a deterministic floor (MAX with persisted severities, generator level, human raise — contextual evidence can only raise it). The producer passes `canonicalBaseRiskClass(...)`; it contains no risk literal (guard test).
- ABA consumes it: `packageIssuancePolicy` refuses (`RISK_POLICY`) a package whose persisted recommendation risk is *below* the action type's canonical base. Unclassified keeps its P0-2 meaning (treated as high, never below a base). The package still records the persisted class; no `aap/1` change.
- Effect on the approval tier: producer-made proposals are now `medium` (required approver tier 2) instead of unclassified/high (tier 3). Test fixtures that used `low` for this action type were updated to `medium` (shared `issuanceFixture`, API `APPROVABLE_FACTS`).

## 3. STOP-AND-REPORT — why Blocks 3–10 were not started
The block text says to stop if the source data cannot be ingested through an existing authoritative DAL path without inventing a new source of truth, and the principal proof forbids direct BO seeding. Four inputs cannot be obtained that way, and two of the four are *deliberate* prior owner rulings:
1. **Item and warehouse identity** have no writer at all. Adding `inventory_item` / `warehouse` mappers plus BO commands extends the existing mapper path (BO stays the truth) but creates a new canonical-entity creation path — a design decision, not a test fixture.
2. **Baseline reorder policy.** A balance created by DAL movements is 0/0/UNSET, and the producer correctly returns no recommendation for an unset baseline (`FIRST_CONFIGURATION_OPTION = NO`). The block asks for "existing reorder policy state" through DAL, but Block E (owner-ruled) forbids the intake path from configuring it. These two cannot both hold.
3. **Declared currency** is a business-admin act by Block C, not a DAL fact.
4. **SIM→ADI.** The locked package chain is BO→BI→DT→SIM→ADI; ADI's package intake takes a Simulation publication package. Under C-1 no simulation exists for this action, so a *package-intake* ADI entry cannot be satisfied without fabricating one. AC-1's producer writes ADI records directly; Block 7 must say whether the BI/BDT boundary is a producer precondition (my proposal) or whether ADI intake is to be amended.

|---|---|---|
| D1 | May DAL gain `inventory_item` and `warehouse` record types (mapper v1 + BO commands that create the canonical rows, scope from context, provenance required, no defaults)? | Yes — the minimum needed; BO remains the only writer. |
| D2 | How does the baseline reorder policy enter? (a) a BO-owned, audited configuration route using the existing `configure_inventory_reorder_policy` command (Block E intact); (b) a new DAL record type (reverses Block E); (c) accept that a DAL-only business has no baseline and the principal proof configures it through (a). | (a) with (c): the proof ingests items, warehouses, movements and costs through DAL and configures the baseline through BO's own command. DAL never sets operational policy. |

| D4 | BI/BDT boundary: producer precondition (published BI insight version + published DT snapshot, digest re-derived from BO truth, mismatch fails closed) rather than amending ADI's SIM-based package intake? | Yes; no simulation is fabricated, C-1 stands. |

On approval of D1–D4 the remaining blocks are: DAL mappers + BO commands (3–4), BI evidence service and DT snapshot service in `packages/workflow` over a BO read port joined at the composition root (5–6), producer boundary (7), the principal real-PostgreSQL proof and the eleven failure proofs (8–9), architecture guards (10), reassessment (11).

## 5. Block 3 — DAL ingestion of the first-action source facts (owner rulings D1–D4 applied)
What changed (Business Operations intake mapper registry and command executor; no migration, no DAL change, no contract change):
- **`inventory_item` v1 and `warehouse` v1 record types (D1)** -> BO commands `create_inventory_item` / `create_warehouse` in `OperationalCommandExecutor`. Identity is a natural key (SKU / warehouse code, strict pattern, bounded names); BO generates the id; scope always from the authenticated context; `source_system = INFINICUS_DA`, `source_record_id = submission#index` (traceable to the DAL provenance record). A replay with identical attributes is a no-op; the same key with different attributes is refused (master data is not changed by intake).
- **`inventory_movement` v3**: the item and warehouse may be addressed by natural key (`sku`, `warehouseCode`) because a source cannot know BO identifiers (exactly one of id/key each), and the record may state its business instant `occurredAt` (demand history; never in the future on the database clock). It maps to `record_keyed_inventory_movement`, which resolves the keys inside the business scope (fail closed) and calls the SAME single movement writer. A v2-shaped record maps exactly as before.
- **Not through DAL, by ruling**: the baseline reorder policy (D2: a later BO-owned route; Block E intact) and the declared currency (D3). The test asserts the balance stays `UNSET` 0/0 and no currency is declared after ingestion.
- Proof: `apps/api/tests/ac2-dal-first-action-ingestion.integration.test.ts` (6 tests, real PostgreSQL, production `buildApp`, production DAL service and BO intake route): DAL accepts 15 records with 15 provenance records and writes no operational row; BO intake canonicalizes warehouse, item, receipt (1000 units, cost 10 USD, business instant 5 days ago), 12 issues on 12 distinct days and the balance (100); replay is idempotent; unknown SKU / future instant / cost without currency each refuse the whole package with nothing persisted; a conflicting master record is refused; scope in the record is ignored and another tenant cannot consume the package.
- Honest limit: the mapper-to-command-to-row path is proven; the BO item/warehouse creation still has no HTTP route of its own (it is intake-only by design).

## 6. Block 4 — Business Operations canonical truth (D2, D3 applied)
- **BO reads what DAL delivered, and only BO**: `InventoryPolicyFactsRepository` (BO's own facts reader) sees the ingested item, the single balance, the latest receipt (cost 10, USD) and the dated demand history (12 issues, 900 units). No BO reader consults a Data Acquisition table; Data Acquisition runtime references no BO or canonical inventory table (architecture guard).
- **Baseline policy (D2)**: new BO-owned route `PUT /v1/businesses/:businessId/inventory-items/:itemId/warehouses/:warehouseId/initial-reorder-policy` (`bo:admin`, Idempotency-Key, audited `bo.reorder_policy.initial_configured`, atomic with the change). It performs the **first** configuration only: the executor refuses (`ReorderPolicyAlreadyConfiguredError`, HTTP 409) a balance that is already `CONFIGURED`, checked under the row lock (`requireState: 'UNSET'`), so changing an existing policy stays an authorized action. Values must be positive, at most four decimals, never rounded. It reuses the single writer (`configureInventoryReorderPolicy` -> `apply_inventory_reorder_policy`, migration 0196); no new SQL, no migration. The DAL intake mappers still cannot produce the command (guard).
- **Currency (D3)**: the explicit business-admin declaration is used as the currency source in the proof; DAL never declares it.
- **Proof** (`ac2-bo-canonical-truth.integration.test.ts`, 7 tests; `ac2-bo-canonical-writer.architecture.test.ts`, 7 guards): with the baseline unset and no currency BO derives nothing (`EVIDENCE_UNAVAILABLE`, `BASELINE_UNSET_OR_ZERO`); the first-policy route configures UNSET -> CONFIGURED once with its audit row; a second call is 409 and changes nothing; unauthenticated / viewer (no `bo:admin`) / other tenant / non-positive, unknown or over-precise values / missing Idempotency-Key are refused; the application role cannot write the reorder columns directly; with baseline and declared currency the BO derivation yields the compliant single step 175/190 from DAL-ingested truth and writes nothing.
- Guards extended additively (no guard weakened): the Block E, B2b, B2c, B2d and Block C architecture guards now list the one new carrier of the command literal (the BO first-policy service) and the one new consumer (the route).
- Honest limit: item and warehouse creation still has no HTTP route of its own (intake only, by design); BI/BDT and the ADI boundary are Blocks 5–7.

## 7. Block 5 — BI evidence of the first action
- **What exists, reused (no new table, no migration):** BI metric definitions (domain `inventory_supply`, once per business), append-only metric calculations and an insight package VERSION that references the calculations by id. Added only additive repository helpers (`findByCode`, `findLatestVersion`, the version's `metricValueIds`, the calculation's `evidenceReference`, which the existing `evidence_reference` column already provided).
- **`InventoryBiEvidenceService`** (`packages/workflow`, BI-owned) reads Business Operations only through a structural read-only port (`InventoryEvidenceFactsService`, BO runtime; joined solely in `apps/api/src/inventoryBiEvidenceComposition.ts`, so BI never imports BO) and writes only BI tables, in ONE shared tenant transaction (a partial evidence set is never visible). Route: `POST /v1/businesses/:businessId/inventory-items/:itemId/bi-evidence` (`bi:write`, active subscription, Idempotency-Key, strict body naming the approved rule-set version, no default).
- **Evidence (descriptive, never fabricated):** `inventory.demand.issued_units` (sum and observation count over the rule set's window), `inventory.stock.on_hand_units` (with the balance's current policy values as stated facts), `inventory.receipt.latest_cost_per_unit` (only when a receipt with a positive cost and currency exists; otherwise no metric and the summary says so). Confidence is null. Each value carries an `evidence_reference` (`source BO`, the BO fact-snapshot digest, capture time, rule-set version, expiry = capture + the rule set's 24 h maximum evidence age) and the same in its dimensions. The currency-consistency flag is computed in BO and carried as-is; BI neither holds nor compares the business currency.
- **Consistency proof:** the digest BI records equals the digest the BO derivation computes from BO truth for the same facts, so BI evidence and BO state are provably the same fact set; ADI (Block 7) will refuse on a mismatch or expiry.
- **Append-only:** each request appends a new version and new calculations (versions 1, 2 ...), reusing definitions. A read side (`getLatest`) is provided for the Digital Twin (Block 6) and ADI (Block 7).
- **Tests:** `ac2-bi-evidence.integration.test.ts` (9, real PostgreSQL: publish with BO untouched; read-back; append-only; no cost -> no cost metric; inconsistent currency recorded as a fact; unknown item / no balance / unapproved rule set publish nothing; atomic rollback; auth, `bi:write`, tenant scope, strict body, Idempotency-Key, replay; tenant isolation) and `ac2-bi-evidence.architecture.test.ts` (6 guards). Three exact-file BO guards were extended additively with the one new read-only BO reader (declared-currency, cost/currency and evaluator-directory guards); nothing was loosened.
- **Placement note:** the BI service lives in `packages/workflow` (the existing home of `TwinComputationService`, the precedent for twin/BI computation) because `layers/business-intelligence` is a placeholder with no runtime wiring; it avoids naming BO cost/currency fields so the existing "workflow does not touch movement cost or currency" guards stand unchanged. Moving it to a BI package later is a pure relocation.
- **Not done:** no BI->DT publication package (Block 6), no ADI change (Block 7), no general analytics, no forecasts.

## 8. Block 6 — BDT current state of the first action's item
- **Locked-spec reading:** the guardrail's BDT owns the "modeled present-state representation ... derived state required for decision modeling" and must not become a second operational source of truth. The minimum compliant design is therefore a **derived** state with **references**, not a copy of BO or BI facts, built on the existing twin lifecycle (the `TwinComputationService` precedent) - no new table, no migration.
- **`InventoryItemTwinService`** (`packages/workflow`) consumes **BI evidence only** (the BI service's read side, structurally; it never imports or reads Business Operations: BO -> BI -> BDT) and publishes one snapshot per request through the existing definition -> instance -> snapshot -> value + evidence -> validate -> publish lifecycle, with its own definition/instance `inventory-item-twin`, in ONE shared tenant transaction (nothing half-built is visible). Route: `POST /v1/businesses/:businessId/inventory-items/:itemId/twin-state` (`dt:write`, active subscription, Idempotency-Key; the body must be empty - the caller asserts nothing).
- **The modeled state** (`inventory-item-twin-state/1`, model `inventory-item-state` v1, method `DETERMINISTIC_RATIO`): average daily demand (demand / window), days of cover (on hand / average demand, null with no demand), policy position (`POLICY_UNSET` / `AT_OR_BELOW_REORDER_POINT` / `ABOVE_REORDER_POINT`), observation count and window. It restates **no raw operational fact** (no stock count, cost or currency; asserted) and references the BI insight package version and metric ids, the BO balance id, the rule-set version and the BO fact digest. Two snapshot evidence rows point at the BI version and the BO facts digest. The snapshot's effective time is the BO capture time of the evidence.
- **Fail closed:** missing BI evidence, evidence past its expiry, an inconsistent evidence set (a metric whose digest or item differs from its version) or an incomplete one publishes nothing and creates no twin structure.
- **Freshness (existing P0-3 rule, unchanged):** a snapshot is superseded when a newer snapshot of the same business is published - including another item's or the operational twin's. That is conservative (fail closed), and it means a recommendation must be based on the newest twin state. Evidence capture time has one-second resolution.
- **Tests:** `ac2-bdt-state.integration.test.ts` (8, real PostgreSQL), `inventoryItemTwinState.test.ts` (5 pure), `ac2-bdt-state.architecture.test.ts` (7 guards). Existing guards extended additively with the one new shared-transaction user and the one new composition file; nothing loosened.
- **Not done:** no BI->DT publication package and no DT->SIM hop (no simulation exists for this action; C-1), no multi-item twin, no forecast, no change to BO or ADI. ADI consumes the twin and BI evidence in Block 7.

## 9. Block 7 — ADI input boundary
- **Rule:** the principal path no longer rests on an ad-hoc BO snapshot. `ReorderPolicyRecommendationProducer` (v1.2.0) now REQUIRES, as constructor dependencies, the BI evidence read side and the BDT twin state (ports; ADI reads no BI or Digital Twin table and writes nothing in BI, BDT or BO other than BO's own evaluation facts bound to the proposal) and refuses - before anything is derived or written - when: BI evidence is missing (`BI_EVIDENCE_MISSING`) or expired, the twin state is missing or expired, the twin was not derived from the latest BI evidence version (`BI_BDT_EVIDENCE_MISMATCH`), a newer Digital Twin snapshot of the business has been published (`BDT_STATE_STALE`, the existing P0-3 freshness rule), or Business Operations facts changed since the evidence was published (`EVIDENCE_DIGEST_MISMATCH`: the digest ADI re-derives from BO truth must equal the one BI and the twin carry).
- **BO stays the oracle:** the numbers still come from the owner-approved rule set and the BO evaluator through the existing deriver port; BI/BDT supply the governed evidence boundary, they do not replace BO's judgement.
- **Proposal and lineage:** the structured proposal (contract unchanged in shape) now cites one `bi_inventory_evidence` reference (the insight package version id) and one `bdt_inventory_item_state` reference (the twin snapshot id), bound to the same fact digest as the BO facts and the four BO evaluations. `BI_BDT_EVIDENCE_REQUIRED` (per `code@schemaVersion`, canonical-actions) makes `proposalEvidenceProblems` demand both, so ABA's capture refuses a proposal without them (tested by stripping the references from a stored proposal). The recommendation version is anchored to the twin snapshot (`twin_snapshot_id`) so the existing approval and issuance freshness gate judges it, and it is time-sensitive until the evidence expires.
- **Permissions:** the producer route now also requires the existing `bi:read` and `dt:read` (no new permission).
- **Related fix:** the twin read side breaks ties between snapshots published within the same second (evidence capture time has one-second resolution) by the BI evidence version, so "latest" is deterministic.
- **Tests:** `ac2-adi-boundary.integration.test.ts` (8, real PostgreSQL: no BI, no BDT, success with the proposal's references / twin anchoring / expiry / nothing written upstream, BI republished, superseded twin, BO facts changed after the evidence, expired evidence, ABA capture refusal without the references), `ac2-adi-boundary.architecture.test.ts` (7), contract tests (+4). The AC-1 E2E, the B2d proof and the ABA authoring tests now publish BI evidence and the twin before producing (their principal proofs, including the unmodified and modified executions, pass unchanged); the two missing-target refusals now report `BI_EVIDENCE_MISSING` because the evidence gate comes first. Existing guards were extended additively (producer imports, composition imports, the BI/BDT composition lists).
- **Not done:** no SIM hop (C-1), no change to ABA authority or BO execution, no LLM, no second action type. The DAL-fed principal proof with every link is Block 8.
