## 1. Recommendation in one paragraph
Do **not** build offline selling in the browser. Build it **only inside the native device shell (8d-2)**, as a small, encrypted, on-device queue of *sale intents* that the server turns into real orders when the connection returns. The server stays the only authority: totals shown offline are **provisional**, clearly marked on the receipt, and the server's total wins on sync; any difference is not hidden but put in an **exceptions list** for the owner. This needs one explicit amendment to the frozen rule "the server computes every total" (exact wording in section 6), one new API endpoint and one migration, and limits (cash only, a time and count cap, no discounts or voids offline). If you do not accept the amendment, the honest alternative is Option A: keep today's behaviour (offline blocks actions, safe retry) and write a downtime procedure.

## 4. The proposed design (Option B)
### 4.1 What works offline
- Taking a sale: add products (from a cached catalogue), quantities, a **cash** tender, change calculation, print or reprint a **provisional** receipt, open the cash drawer.
- A "card (terminal-confirmed)" tender may be recorded **with its reference only if you allow it** (decision D5). The platform never processes cards; the external terminal does, and offline card approvals can be declined later. Default: **cash only offline**.

### 4.2 What does not work offline (and says so)
Opening or closing a register, voiding, **discounts** (they need an owner or admin check), refunds, editing a product or price, changing printers, sales history. These stay online-only.

### 4.3 What is stored on the device
Only what is needed to sell and to sync: a catalogue snapshot (names, prices, the time it was taken), the **open register session** it was opened against, and the queue of sale intents. **Never** card data, passwords, tokens or customer personal data (the note field keeps its existing rules: 1–500 characters, no card-like digits). The database is **encrypted** with a key held in the platform's secure keystore, behind the cashier's PIN or device lock.

### 4.4 A sale intent (one queued record)
`client_sale_id` (a UUID, the idempotency identity), device id, business, register session id, the cashier (user) id, `device_created_at`, lines (`product_id`, quantity, **the unit price the device showed**), the **provisional total** the device computed, tenders (method, amount tendered, reference), the catalogue snapshot time, and a status (`queued`, `sending`, `accepted`, `needs_review`).

## 5. How the sync works
### 5.1 New endpoint (needs a migration and its own window)
`POST /v1/businesses/:id/offline-sales` (permission `bo:write`, Idempotency-Key = `client_sale_id`). The server, in **one transaction**:
1. checks the register session is the business's and was valid, the product ids belong to the business, quantities and currency are exact;
2. **recomputes every line and the total itself** with the same minor-unit rules and the product prices;
3. compares with the device's provisional total and prices (5.4);
4. creates the order, lines, payments and completion through the **existing** paths, so every existing invariant still applies (append-only payments, the consistency trigger, the register link);
5. records an **offline-sale record** (the device's claims, the server's result, the difference if any) in a new append-only table.

Replaying the same `client_sale_id` returns the first answer. A device that crashes mid-sync is safe.

### 5.2 Outcomes (never silent)
| Outcome | When | What happens |
|---|---|---|
| `accepted` | server total equals the provisional total and every price matches | order completed normally; receipt number issued |
| `accepted_with_difference` | totals differ **only** because of a price drift the policy allows (5.4) | order completed at the device's price, the difference is recorded and shown |
| `needs_review` | the sale cannot satisfy the payment invariant (for example the server total is **larger** than what was paid), the register session was closed meanwhile, or a product is gone | **no order is created**; the intent is kept in an **exceptions list** for an owner or admin to resolve (accept with a recorded reason, or reject) |

### 5.3 Numbers and time
The device prints a temporary number `OFF-<device>-<sequence>`; the server issues the real `ORD-…` and the device shows the mapping after sync. The device clock is **not trusted**: the server stores `received_at` next to `device_created_at` and flags a large skew. The order date uses the device time only when the skew is within a small bound; otherwise the server time.

### 5.4 Price drift (the hard part)
The server recomputes with the **prices it had at the time of the sale**. The catalogue snapshot carries its timestamp. A product's `updated_at` (maintained by the existing trigger) tells whether it changed after that snapshot:
- **unchanged since the snapshot** -> the device price is valid -> `accepted`;
- **changed after the snapshot** -> `accepted_with_difference` if you choose to honour the price the customer was shown (recommended, decision D4), else `needs_review`.
This needs **no new price-history table**; it is conservative (any product edit triggers review), which is the safe direction.

### 5.5 Identity and expiry
A queued sale belongs to a signed-in cashier. Syncing needs a valid session; if it has expired the queue waits and shows "sign in to send N sales". The scope (tenant, workspace, business) is stored with each intent and re-verified by the server, as on every request. A sale queued under one workspace can never be sent under another.

## 6. The rule amendment you would be approving (exact wording)
> **Current:** "The server computes every total."
> **Proposed:** "The server computes every **final** total. A device without a connection may show and print a **provisional** total, computed with the same exact minor-unit rules, labelled provisional. The server recomputes it on sync; the server's total is the record, and any difference is stored and surfaced, never hidden."

Provisional receipts must say, in plain words and in the receipt's language, that the document is provisional and that the final receipt number is issued after sync. They are not tax documents.

## 8. Risks and what limits them
| Risk | Limit |
|---|---|
| Money recorded that the customer did not actually pay (device total too low) | exceptions list; **provisional totals use the shared exact-math library and are compared with the server on every sync**; a cap on offline duration and on the number and value of queued sales (D3) |
| Lost or stolen device with queued sales | encryption at rest + PIN; the queue holds only business data, no card data; a stated procedure to revoke the device's sign-in; unsent sales are lost with the device (cash was taken: record it on paper) |
| Duplicate sale on retry | `client_sale_id` idempotency, bound to the resource (as #203) |
| Two devices sell the same stock offline | the platform has no stock enforcement on sale today; recorded as a known limit |
| Price changed while offline | 5.4 |
| Register closed on another device while this one sold offline | `needs_review` |
| Clock wrong on the device | stored skew, server time as fallback |
| Staff abuse (sell offline, never sync) | the cap forces a sync; the unsent count is visible; an owner report of devices with unsent sales (9e) |
| Scope creep to card payments offline | out of scope; cash only unless D5 says otherwise |

## 9. Test strategy (when built)
- **Property tests**: for random carts and quantities across KWD, USD and JPY, the device's provisional total equals the server's recomputed total byte for byte; any code path that rounds differently fails the build.
- **Fault injection**: kill the app mid-sync, replay a batch, send the same sale from two devices, expire the session mid-queue, change a price while offline, close the register elsewhere, skew the clock; each ends in a defined outcome from 5.2, never a half-created order.
- **Invariant tests** on the server: an offline sale can never produce an order whose payments do not equal its total (the existing database constraint is the backstop).
- Local PostgreSQL proof and CI as for every migration block; a rollback block in the window plan.
