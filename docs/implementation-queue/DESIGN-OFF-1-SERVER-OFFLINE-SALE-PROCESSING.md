## 1. Objective
Define the server side of offline selling: how a cash sale queued on a device (OFF-2/OFF-3) is accepted, recomputed and recorded when it syncs. The server's final total is always the record (amendment, record section 2). Anything the server cannot complete without bending an existing invariant is **kept on an exceptions list and creates no order**.

## 4. Proposed server design
### 4.1 Endpoint
`POST /v1/businesses/:id/offline-sales` with the existing chain from F-8 (`bo:write`, active subscription, `requireBusinessWorkspace`, `requireIdempotencyKey`). The Idempotency-Key **equals** `client_sale_id`; a mismatch is refused. The same replay-binding rule as #203 applies (a key is bound to the resource it first created).

Request (one sale intent; field names are proposals, finalised in step 2):
`client_sale_id` (uuid), `device_id`, `register_session_id`, `device_created_at`, `catalogue_snapshot_at`, `currency_code`, `lines[] { product_id, quantity (positive integer), unit_price_shown }`, `provisional_total`, `tenders[] { method: "cash", amount_tendered, reference? }`.

Rejected at the door (HTTP 400/409, nothing stored): unknown or non-`cash` method (D5); more than the allowed lines; non-positive quantities; amounts that are not exact for the currency's minor unit; unsupported currency; `device_created_at` older than the D3 duration cap relative to the server receive time; a body that fails schema validation. Discounts, refunds, voids and register open/close are **not** accepted offline (design memo 4.2).

### 4.2 Processing (one transaction, tenant context as on every request)
1. Look up an existing `offline_sales` row for `(business_id, client_sale_id)`. If present: return the **first** recorded answer (replay-safe, including `needs_review`).
2. Verify the register session belongs to this business and its currency equals the request currency. If the session is closed, or was not open at `device_created_at`: outcome `needs_review` (nothing else is written except the exception record).
3. Load each product `FOR SHARE` with `business_id` match. Missing, inactive or foreign product: `needs_review`.
4. Recompute every line and the total in **integer minor units** from the **current** server prices (the server's price is the record).
5. Compare with the device: for each line, `unit_price_shown` vs server price; and `provisional_total` vs server total. Apply the drift policy (section 6) to every difference.
6. If all lines match, or every difference is allowed by section 6: create the order bound to the **requested** register session (the online `create` binds the currently open session, so a bound-session variant is needed), add lines at the **price the customer was shown** where section 6 allows it, and complete it through the existing `complete` path with the cash tenders. The F-5 trigger still enforces payment = total.
7. If the server total would exceed what was tendered, or any other existing invariant would fail: **no order is created**; outcome `needs_review`.
8. Write the `offline_sales` record (4.3) in the same transaction in every case, so nothing is silent.

### 4.3 Data model (proposal; migration number 0211 or later, decided at step 2)
- `business_operations.offline_sales` — **append-only** (same `forbid_mutation` + truncate guard pattern as 0206), RLS enabled and forced, tenant/workspace/business columns, composite FKs `(…, business_id)` like 0203. Columns: `client_sale_id` (unique per business), `device_id`, `register_session_id`, `order_id` (nullable: null when no order was created), `outcome` (`accepted | accepted_with_difference | needs_review`), `review_reason` (code), `device_created_at`, `received_at` (server clock), `clock_skew_seconds`, `catalogue_snapshot_at`, `device_total`, `server_total`, `difference`, `currency_code`, `request_digest` (sha-256 of the canonical request), `lines_detail` (jsonb: the device's claims and the server's result per line), `correlation_id`, `created_at`.
- `platform.orders.client_sale_id uuid NULL` with a partial unique index per business, so an order can be traced to its sale and a second order for one sale is impossible even if the table row were lost.
- **Resolution of an exception is OFF-4** (D8). OFF-1 only stores `needs_review`; it adds no resolve endpoint. A later resolution is a **new** append-only row, never an update.

### 4.4 Time and numbers
- The device clock is not trusted: store `received_at` (server) next to `device_created_at`. Use the device time as the order date only when `|skew| ≤ a small bound` (value chosen at step 2 and listed for owner approval); otherwise server time. A larger skew is recorded, not hidden.
- Provisional numbers `OFF-<device>-<sequence>` are device-side (OFF-3). The server issues the real `ORD-…` number and returns the mapping.

### 4.5 Response
`{ outcome, order_id?, order_number?, server_total, device_total, difference, review_reason? }`. The server total is always returned and is the record. A replay returns the first answer with HTTP 200.

## 5. Outcomes (never silent)
| Outcome | Condition | Effect |
|---|---|---|
| `accepted` | totals and every price equal | order completed normally |
| `accepted_with_difference` | the only differences are allowed by section 6 | order completed at the shown price; difference stored and surfaced |
| `needs_review` | any other condition (underpayment vs server total, closed or foreign session, missing/inactive product, drift beyond policy, unsupported input discovered after the door) | **no order**; exception stored for an owner/admin (D8, OFF-4) |

## 6. D4 price-drift policy (owner accepted 2026-10-21)
### 6.1 Rule
The customer-shown price is honoured **only if all hold**:
1. the product **changed after** the catalogue snapshot the device used (its `updated_at > catalogue_snapshot_at`) — an unchanged product whose price nonetheless differs is a data error and goes to review;
2. the **difference per line, and for the whole sale, is within the owner-set limit for the currency** (6.3);
3. the shown price is **not lower than zero** and the line is a normal catalogue line (no manual or negative-price line offline).

Everything else goes to `needs_review`. Every honoured difference is recorded with the old and new price and is visible (never hidden).

### 6.2 What this deliberately does not do
- No new price-history table (design memo 5.4): the product's `updated_at` is the only signal. It is conservative: any product edit after the snapshot is treated as possible drift, never as proof of an acceptable price.
- A product edit that is not a price change (for example a rename) also triggers the check; if the price is equal it is simply `accepted`.

### 6.3 Limits are parameters, not invented numbers
- The tolerated drift per currency is an **owner-set parameter**, like the D3 monetary cap. Its storage (a business-level setting versus configuration) is decided at step 2.
- **Until a limit is set for a currency, the limit is zero**: any price difference goes to `needs_review`. This fails closed and cannot be loosened by omission.
- OFF-1 sets no figure. Offline selling remains blocked from being switched on (D3 caps).

## 7. Invariants OFF-1 must not weaken
Server authority over **final** totals · integer minor-unit accounting (KWD 3, USD 2, JPY 0; no float money in the new code) · append-only financial records · payments sum exactly to the order total (F-5 trigger untouched) · idempotency by `client_sale_id` · tenant + workspace + business isolation with forced RLS (the schema has no branch concept) · existing `bo:read/bo:write/bo:admin` (no new permission) · NA-04 browser-storage restrictions (not touched) · no card data (D5) · device clock not trusted.

## 8. Test plan (for step 5; stated now so the design is checkable)
Real-PostgreSQL integration tests, each with a mutation proof that it fails when the guarded rule is removed:
- replay of the same `client_sale_id` returns the first answer and creates one order; a concurrent pair creates one;
- cross-tenant, cross-workspace and cross-business refusal; wrong register session; closed session → `needs_review`, no order;
- price-drift matrix: unchanged/equal, changed-within-limit, changed-over-limit, limit unset (zero), unchanged-but-different, negative price;
- underpayment → `needs_review` and **no order row**; exact payment; overpayment with change on cash;
- missing, inactive and foreign product → `needs_review`;
- minor-unit edges for KWD, USD, JPY; a sale that rounds differently from the device;
- online-equivalence: for the same lines, the offline total equals the online `addLineItem`/`complete` total (the F-7 finding);
- clock skew within and beyond the bound; stale `device_created_at` beyond 24 h refused at the door;
- the `offline_sales` row is append-only (update/delete/truncate refused) and RLS-forced;
- route-permission test (`routePermissions.test.ts`) and a static guard that the route uses the full F-8 chain.
